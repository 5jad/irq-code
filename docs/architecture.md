# معمارية IRQ 0.1 (خطة تنفيذ)

## القرار: Rust للمترجم، استقلال للغة

Rust مناسب لبناء المترجم لأنه يوفر أنواعاً قوية وأدوات اختبار وحزماً ناضجة. هذا لا يعني أن IRQ ترث تلقائياً ضمانات Rust؛ يجب أن يكون لكل ضمان مدقق أو سياسة تنفيذ محددة. نبدأ بتوليد Rust لتقليل كلفة backend، ونحافظ على HIR/IR مستقلة كي نستطيع استبداله لاحقاً.

## تدفق البيانات

1. **SourceMap** يحفظ الملفات والمديات النصية.
2. **Lexer** ينتج tokens ومواقعها، ولا يرفض التنسيق؛ التنسيق وظيفة `fmt`.
3. **Parser** يحول tokens إلى AST ويصدر تشخيصات قابلة للاسترداد.
4. **Name resolution** يحل الوحدات والأسماء والاستيرادات.
5. **Type checker** يفحص الأنواع، exhaustiveness، الأخطاء، والاستعمال.
6. **Effect checker** يجمع صلاحيات `reads` و`writes` عبر الاستدعاءات.
7. **HIR** تمثيل مُطبّع بعد حل الأسماء والأنواع.
8. **Contract checker** لاحقاً: نطاق محدود موثق من الشروط، ثم SMT أو runtime checks عند الحاجة.
9. **Backend** يولد Rust مؤقتاً؛ لاحقاً يمكن إضافة backend آخر دون تغيير دلالة IRQ.
10. **Runtime/capability layer** يفرض الصلاحيات فعلياً عند حدود الملفات والشبكة، لا بالاكتفاء بالفحص الساكن.

## حدود MVP

- دوال، متغيرات، الأنواع الأساسية، `struct` و`enum`.
- `if`, `match`, `return`.
- أنواع النتائج والأخطاء، مع معالجة exhaustive.
- فحص الأنواع والأسماء ورسائل JSON مستقرة.
- لا ملكية مخصصة ولا SMT ولا FFI ولا صلاحيات نظام ملفات في أول نسخة.

## اختبارات القبول

- اختبارات lexer/parser لكل قاعدة نحوية.
- اختبارات compile-pass وcompile-fail مع كود تشخيص ثابت.
- اختبارات golden لواجهة JSON.
- لا يُقبل ادعاء أمني إلا باختبار يثبت أن الفحص أو runtime enforcement يمنع التجاوز.
