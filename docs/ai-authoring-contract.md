# عقد كتابة IRQ بواسطة نماذج الذكاء الاصطناعي

هذا المستند يحوّل نتائج `ai-code-risk-research.md` إلى متطلبات قابلة للتنفيذ للمترجم، والـCLI، وأدوات توليد الكود. الهدف ليس أن «يفهم النموذج اللغة» وحده؛ الهدف أن يكون التفاعل بين النموذج والمواصفة والمدقق محدداً وقابلاً للقياس.

## 1. المبدأ

نتعامل مع النموذج ككاتب كود سريع لكنه قابل للخطأ. لا نعامل النص الذي يولّده على أنه صحيح أو آمن لمجرد أنه يترجم أو يبدو مقنعاً. المصدر النهائي الذي يسمح ببنائه هو برنامج اجتاز الفحوص المحددة، مع بقاء حدود تلك الفحوص معلنة.

## 2. ربط أنماط الخطأ بمتطلبات اللغة

| نمط الخطأ المرصود | دعم IRQ المطلوب | طريقة الاختبار |
| --- | --- | --- |
| سوء فهم الطلب أو تجاهل قيد | مدخلات ومخرجات وعقود صريحة؛ كشف الشروط غير الملباة | أمثلة صحيحة وخاطئة واختبارات postcondition |
| نسيان الحالات الطرفية | `match` شامل، أنواع اختيارية/نتائج، حدود الأنواع الحسابية | اختبارات boundary ورفض المطابقة الناقصة |
| نوع إدخال أو إرجاع خاطئ | فحص أنواع ساكن ورسالة expected/found | compile-fail tests لكل موضع نوع |
| API أو رمز مختلق | حل أسماء مركزي؛ لا يسمح باستدعاء غير معروف؛ مرجع مكتبة آلي | اختبارات لأسماء دوال وحقول غير موجودة |
| كود غير مكتمل | التحقق من اكتمال AST، كل المسارات ترجع، وعدم وجود placeholders في build | ملفات مبتورة وحالات missing return |
| انحياز للـprompt أو اعتبارات غير مطلوبة | مواصفة مهمة محدودة، imports وcapabilities allow-list، فرق واضح بين البيانات والتعليمات | مهام بأوصاف متعارضة وبيانات تحوي تعليمات خبيثة |
| خطأ أمني رغم صحة الوظيفة | واجهات آمنة افتراضياً، فحص أمن مستقل، قدرات مفروضة وقت التشغيل | اختبارات أمنية مع adversarial inputs وسلوك متوقع |
| إصلاح يولد خطأ جديداً | rerun كامل الاختبارات والفحوص بعد أي تعديل | إصلاحات mutation/regression واختبارات corpus |

## 3. مواصفات المهام التي تصل إلى النموذج

كل مهمة توليد تستخدم غلافاً منظماً يحتوي على:

- هدف المهمة ومعيار قبول قابل للتحقق.
- تواقيع الدوال والأنواع المتاحة والملفات المرجعية ذات الصلة.
- قائمة API موثوقة من المشروع؛ لا يطلب من النموذج تخمين أسماء المكتبات.
- قدرات التشغيل المسموحة، والموارد المحظورة، وحدود الحجم/الوقت عند توفرها.
- حالات نجاح وفشل متوقعة، بما فيها المدخلات الحدّية ذات الصلة.
- طريقة الإخراج المطلوبة: ملف IRQ كامل أو تعديل محدد، لا نص مختلط بشرح.
- سياسة صريحة: عند نقص معلومة جوهرية يطلب النموذج توضيحاً بدلاً من اختراع افتراض.

اللغة لا تستطيع إصلاح متطلبات غامضة تلقائياً. إذا لم يكن معيار القبول أو صلاحية الفعل الخارجي محدداً، يجب أن تتوقف العملية قبل التنفيذ أو تطلب قراراً.

## 4. عقد التشخيصات للموديل

كل تشخيص مستقبلي يجب أن يطابق JSON Schema منشوراً وثابت الإصدار. الحقول المقترحة:

```json
{
  "schema_version": "1",
  "status": "error",
  "diagnostics": [
    {
      "code": "E0201",
      "kind": "unknown_name",
      "severity": "error",
      "message": "unknown function `fomat`",
      "primary_span": {
        "file": "app.irq",
        "start_byte": 120,
        "end_byte": 125,
        "line": 8,
        "column": 14
      },
      "expected": null,
      "found": "fomat",
      "help": "check the spelling or import a declared function",
      "fixes": []
    }
  ]
}
```

قواعد واجهة التشخيص:

- `code` ثابت، و`schema_version` يتيح تطوير البروتوكول دون كسر الأدوات.
- span يحدد المصدر بدقة؛ إزاحة البايت هي المرجع، والسطر/العمود لتسهيل القراءة.
- `message` للعرض، أما التصنيف والحقول المنفصلة فللآلات.
- `fixes` فارغة إن لم يوجد إصلاح آمن واضح؛ لا يختلق compiler تعديلاً.
- لا تدمج أخطاء غير مترابطة تحت تشخيص واحد، ولا تنتج ضجيجاً متسلسلاً من الخطأ الجذري نفسه.
- لا تضمن تلميحات التصحيح سلامة التغيير. يجب إعادة فحص المشروع كاملاً.

## 5. حلقة التوليد والفحص والإصلاح

1. تحويل الطلب إلى مواصفة مهمة ومدخلات وأنواع وصلاحيات.
2. توليد كود IRQ ضمن grammar؛ يمكن استخدام constrained decoding لتقليل أخطاء النحو فقط.
3. تشغيل parser وحل الأسماء وفحص الأنواع والأخطاء والآثار.
4. تشغيل الاختبارات والتحليل الأمني ضمن بيئة معزولة، بصلاحيات افتراضية صفرية.
5. إعادة التشخيصات المنظمة إلى النموذج مع الجزء ذي الصلة من المصدر فقط.
6. يسمح بعدد إصلاحات محدود وقابل للضبط؛ بعد استنفاده يتوقف النظام للتوضيح أو المراجعة البشرية.
7. بعد كل إصلاح يعاد تشغيل جميع الفحوص والاختبارات؛ لا تنفذ آثار خارجية قبل نجاح المسار وموافقة المستخدم عند الحاجة.

التوليد المقيد يمنع بعض أخطاء النحو، لكنه لا يمنع كوداً منطقياً أو أمنياً خاطئاً. وكذلك نجاح compiler لا يثبت سلامة البرنامج خارج خصائص الفحص المطبقة.

## 6. الحد الأدنى لمتطلبات الأمان

- اعتبر كود النموذج ومدخلاته غير موثوقين.
- لا تمرر أسراراً أو مفاتيح إنتاج إلى سياق التوليد أو بيئة الاختبار.
- لا تمنح صلاحيات افتراضية للملفات أو الشبكة أو العمليات؛ المنح يكون صريحاً ومحدوداً.
- فرض القدرات في runtime/container/OS؛ تقرير `effects` وحده تحليل وليس sandbox.
- افصل توليد الخطة/الكود عن تنفيذ فعل ذي أثر خارجي.
- طلب موافقة بشرية للأفعال المدمرة أو المالية أو التي تنشر بيانات، إن كانت ضمن نطاق المنتج.
- تعامل مع المكتبات الخارجية و`extern trust` كحد ثقة منفصل يخضع للمراجعة والفحص.

## 7. كيف نقيس «مفهومة للذكاء الاصطناعي»؟

لا نقيس ذلك بانطباع بشري أو بقصر الصياغة وحده. نستخدم benchmark ثابتاً بإصدارات معلنة، ونقارن النموذج نفسه والمهمة نفسها في IRQ وRust/Python أو صيغة أدوات منظمة. نسجل:

- نسبة اجتياز اختبارات الصحة الوظيفية والأمن من المحاولة الأولى.
- نسبة قبول parser/type/effect checker، منفصلة عن الصحة النهائية.
- عدد دورات الإصلاح، وحالات الإصلاح الذي كسر اختباراً ناجحاً.
- عدد العيوب الأمنية المتبقية ونوعها بعد التحليل والمراجعة.
- تكلفة التوكنز وزمن التوليد والبناء والتشغيل.
- أداء الحالات الحدّية والمطالبات الناقصة والـprompt injection في البيانات.

تنشر الأسئلة، والإصدارات، والـprompts، والاختبارات، وحدود الثقة. وتفحص عينة بشرية لأن أدوات التحليل نفسها لا ترى كل العيوب. لا نعلن تفوق IRQ إلا إذا تحسن مقياس محدد دون إخفاء المقاييس التي تراجعت.

## 8. الربط بالخارطة

هذه المتطلبات موزعة على مراحل المواصفات، والـparser/diagnostics، وفحص الأنواع، والصلاحيات وruntime، والاختبار مع النماذج، ومراجعة الأمان. المرجع البحثي الذي ولّدها هو `docs/ai-code-risk-research.md`، والحدود الحالية موثقة في `docs/irq-mvp-spec.md`.
