# مواصفة IRQ — نطاق MVP المقترح

**الحالة:** مسودة قرارات للنسخة الأولى، وليست مواصفة 1.0 نهائية. الغرض منها توجيه التنفيذ والاختبارات. أي تعديل لاحق يجب أن يغيّر هذه الوثيقة والاختبارات المرجعية معاً.

## 1. الهدف والنطاق

IRQ لغة مصدرها مستقل عن لغة تنفيذ المترجم، وموجهة للكود المولّد آلياً الذي يجب فحصه قبل التنفيذ. المترجم نفسه مكتوب بـRust، وRust backend مؤقت. لا يعني ذلك أن قبول Rust للكود المولّد يثبت صحة IRQ أو أمانه.

هدف MVP هو اختبار الفرضية: هل الصياغة المحددة، والفحص السابق للتشغيل، والتشخيصات الآلية تساعد النماذج على إنتاج برامج صحيحة أكثر؟ لذلك يبدأ MVP بنواة صغيرة بدلاً من محاولة دعم كل المجالات أو كامل مواصفات IRQ دفعة واحدة.

## 2. ما يدخل MVP

- ملف واحد ووحدة واحدة باسم `mod`.
- دوال خاصة وعامة، معاملات ذات أنواع صريحة، ونوع إرجاع صريح.
- الأنواع الأساسية: `i32`, `u32`, `i64`, `u64`, `bool`, `str`, و`()`.
- متغيرات محلية مع تهيئة صريحة، وإسناد للمتغيرات القابلة للتغيير فقط.
- تعبيرات literals، أسماء محلية، استدعاءات دوال، أقواس، عمليات حسابية ومقارنة ومنطقية محددة في التنفيذ.
- تعليمات `let`, assignment, `if/else`, `return`، وتعامل مبدئي مع الأخطاء.
- الهدف المستقبلي: تحليل `reads` و`writes` عبر استدعاءات IRQ؛ هذا الفحص غير منفذ حالياً، ولا يُعد بأي حال عزلاً أمنياً للنظام.
- الهدف المستقبلي: تقييم `requires` و`ensures` وقت التشغيل، لا كإثبات ساكن؛ التقييم غير منفذ حالياً.
- CLI `check`, `emit-rust`, و`build` إلى مكتبة Rust للـsubset الحالي؛ `run/test` الكامل وتشخيصات backend المرتبطة بمصدر IRQ مؤجلة.

## 3. ما يؤجل

تؤجل إلى ما بعد MVP: generics، traits، المراجع والملكية المخصصة، `struct` و`enum` و`map` و`set` و`list`، التزامن، FFI، جسور Python/Rust من المستخدم، sandbox إنتاجي، إثبات SMT، وbackend أصلي. لا نعد بسلامة ذاكرة أو عزل موارد قبل تنفيذ واختبار تلك الأنظمة فعلياً.

## 4. القواعد الأولية للنحو

المقتطف التالي هو grammar الهدف الأولية، وليس مطابقاً بالكامل للـparser الحالي. القواعد التي يقبلها parser فعلياً موثقة في [implemented-subset.ebnf](implemented-subset.ebnf)، ويجب تحديثها مع الاختبارات عند كل توسعة.

```ebnf
module       = "mod", identifier, newline, { newline | function } ;
function     = [ "pub" ], "fn", identifier, "(", [ parameters ], ")", "->", return_type, newline,
               indent, "reads:", effect_list, newline,
               indent, "writes:", effect_list, newline,
               indent, "requires:", expression, newline,
               indent, "ensures:", expression, newline,
               indent, "body:", newline, block ;
parameters   = parameter, { ",", parameter } ;
parameter    = identifier, ":", type ;
effect_list  = "none" | effect, { ",", effect } ;
return_type  = type, [ "|", "err(", error_name, { ",", error_name }, ")" ] ;
block        = statement, { newline, statement } ;
```

هذه نية التصميم المستقبلية. حالياً يعتمد parser على مسافات ثابتة داخل أجسام الدوال، ولا يوجد أمر `irq fmt` بعد.

## 5. دلالات الأخطاء والحساب المقترحة وحالة التنفيذ

- الدلالة المستهدفة: `a / b` لا يُنفذ عند `b == 0`؛ نتيجة هذه الحالة خطأ معلن `DivByZero`.
- قسمة أصغر عدد سالب على `-1` في الأنواع الموقعة ترجع `Overflow`، ولا يسمح بسلوك غير محدد.
- العمليات الصحيحة العادية لا تلتف بصمت. Rust emitter الحالي يحول العمليات المدعومة إلى `checked_add/sub/mul/div/neg` ويرجع `IrqRuntimeError::Overflow` عند الفشل.
- الالتفاف لا يكون إلا بصيغة صريحة مخصصة، وبعد إضافة اختبارات الحدود.
- نتائج العمليات العشرية وNaN وInfinity مؤجلة حتى تعريف دلالاتها واختبارها.
- لا يعتمد الكود على سلوك backend أو Rust الخاص عند overflow؛ سلوك IRQ هو المرجع.

**المنفذ حالياً:** يرفض الفاحص المقام الثابت الذي يساوي صفراً أو يُحسب إلى صفر، ويفحص مجال literals والتعابير الصحيحة الثابتة بحسب النوع المتوقع. `irq emit-rust` ينتج دوال Rust تعيد `Result<T, IrqRuntimeError>`؛ و`irq build` يشغل `rustc` لإنتاج مكتبة للـsubset مع checked arithmetic وكشف المقام الديناميكي و`MIN / -1`. البناء ينشر artifact بعد نجاح الترجمة فقط، ولا ينشئ برنامجاً تنفيذياً أو يشغله؛ التوليد محدود بالـsubset، والعقود والآثار والعزل ليست منفذة.

## 6. دلالات العقود المستهدفة (غير منفذة)

الخطة هي أن يفحص `requires` عند مدخل الدالة و`ensures` عند الرجوع الناجح فقط. التنفيذ الحالي لا يفسر ولا يشغل هذه العقود؛ parser يتحقق فقط من وجود القسم وترتيبه.

العقود في هذا النطاق دفاع إضافي وليست بديلاً عن فحص الأنواع أو الاختبارات. يجب عدم السماح بتقييم عقد يتسبب في overflow غير معرّف؛ إما يستخدم evaluator دقة رياضية آمنة أو يرفض التعبير غير المدعوم.

## 7. دلالات الصلاحيات المستهدفة (غير منفذة)

الخطة المستقبلية أن يحلل الفاحص أثر الاستدعاءات بين دوال IRQ ويكشف عدم تطابق التصريح. التنفيذ الحالي لا يحلل `reads` و`writes` دلالياً. لا يجوز اعتبار أي تصريح أثَر sandbox؛ فرض صلاحيات الملفات والشبكة يتطلب capabilities فعّالة واختبارات traversal وsymlink وTOCTOU.

## 8. سياسة الرفض والإصلاح

- المترجم يرفض البرنامج عند خطأ نحوي أو دلالي، ويخرج code ثابتاً وموقعاً ورسالة منظمة.
- الإصلاح المقترح للذكاء الاصطناعي advisory فقط؛ لا يطبق المترجم تغييرات دلالية تلقائياً.
- `irq fmt` يصلح التنسيق فقط ولا يغيّر المعنى.
- بعد أي إصلاح يعاد تشغيل كامل مراحل الفحص والاختبارات، لا يكتفى بإعادة فحص السطر المعدل.

## 9. قرارات القبول والاختبارات

قبل الانتقال من نواة parser إلى type checker، يجب أن توجد حالات اختبار مثبتة تشمل:

1. ملفات سليمة بتوقيعات صحيحة، وأخطاء syntax محددة مع line/column.
2. رفض إعادة تعريف اسم أو استخدام متغير غير معرف.
3. رفض إسناد لمتغير ثابت ونوع إرجاع غير مطابق.
4. رفض تجاهل نتيجة عملية قابلة للفشل.
5. مسارات قسمة: صفر، قيمة موجبة وسالبة، `MIN / -1`، وحدود النوع.
6. عقد نجاح يمر وعقد يفشل وقت التشغيل مع تصنيف واضح.
7. تصريحات آثار صحيحة وغير صحيحة عبر استدعاء دالة أخرى.
8. ضمان أن تقرير الأثر لا يُعرض للمستخدم على أنه عزل runtime.

## 10. معايير الخروج من مرحلة المواصفات

- [ ] grammar كاملة لكل subset الذي سينفذ في MVP، لا للميزات المؤجلة.
- [ ] نتائج حسابية وأخطاء محددة بأمثلة حدّية.
- [ ] تمثيل موحد للأخطاء ونتائج الدوال.
- [ ] دلالات العقود runtime موثقة ومتميزة عن الإثبات.
- [ ] تمييز واضح بين تحليل آثار ساكن وفرض الصلاحيات وقت التشغيل.
- [ ] corpus أمثلة pass/fail قابل للتشغيل آلياً.
