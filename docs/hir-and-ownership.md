# HIR والملكية في IRQ — الحالة والحدود

## الحالة الحالية

أُضيف `irq-hir` كتمثيل وسيط typed منفصل عن AST وRust backend. يحول `lower` الوحدة التي اجتازت الفحص الساكن إلى عقد HIR للأنواع scalar والتعابير والتعليمات المنفذة حالياً. يشغّل CLI هذه المرحلة بعد `irq-check`، ويذكرها في نتيجة `irq check`.

الـHIR الحالي ليس بعدُ HIR مُطبّعاً بالكامل: لا يحمل spans لكل عقدة، ولا يملك CFG أو SSA أو بيانات effects، وما زال Rust emitter يقرأ AST مباشرة. lowering يقبل AST صالحاً بعد checker؛ لا يُقصد به أن يحل محل التحقق الساكن.

## قرار ملكية مؤقت

نطاق IRQ 0.1 المعياري يعتمد value semantics ولا يتضمن references أو borrowing أو collections. لذلك لا نضيف حالياً `&T` أو `&mut T` إلى مصدر IRQ، ولا ندعي أن توليد Rust وحده يثبت سلامة الذاكرة. تمثيل HIR الحالي يعبّر عن locals وعمليات قيمة فقط.

أي توسيع مستقبلي للمراجع يتطلب قراراً لغوياً مستقلاً، ثم نموذجاً موثقاً لـmove/copy، ونطاقات الاقتراض والتداخل عبر الاستدعاءات، واختبارات قبول/رفض عدائية، ومراجعة مستقلة قبل أي ادعاء سلامة. إلى أن يحدث ذلك، يظل ownership/borrowing خارج الضمانات المنفذة.

## حد الوحدات

مواصفة IRQ 0.1 تنص على وحدة واحدة وتحظر `use` والوحدات متعددة الملفات. مهام خارطة الطريق الخاصة بتحميل مشروع واستيراد وحدات تتطلب قرار إصدار/مواصفة جديداً أو تغييراً صريحاً لنطاق 0.1؛ لن يقبل compiler ملفات متعددة بصمت قبل حسم التوافق، وسيبقى module resolution غير منفذ في هذه الدفعة.
